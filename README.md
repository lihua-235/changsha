# 长沙美食可信度评估与个性化行程生成系统

> 在网红城市里，平台评分已经不能代表「本地人觉得好吃」。
> 本项目以长沙为单城试点，构造不依赖评分的本地偏好信号，识别真正值得吃的店，
> 并生成按预算分档的可执行行程。

**状态**：Phase 1 已完成（数据、抽样、标注规范就绪），Phase 1.5 人工标注进行中（0 / 150）

---

## 为什么做这个

平台评分不是中立的。我们采集长沙 6 个片区 9,560 家餐饮 POI 后，对其中 8,021 家
同时具备评分与人均价的店铺做了相关性分析：

| 指标 | 结果 |
|---|---|
| 评分 vs 人均价 Spearman ρ | **0.469** |
| 评分 ≥ 4.5 的店，人均中位数 | **55 元** |
| 评分 < 3.5 的店，人均中位数 | **19 元** |
| 人均 15 元以下 / 30–60 元 / 60–120 元以上 的评分中位数 | 3.9 / 4.3 / 4.5 |

结论：**评分体系系统性偏向中高价店铺**。按「评分排序」生成攻略，预算有限的旅行者
会被系统性地推离真正值得吃的低价好店。而这类用户恰恰是最需要一份可靠攻略的人。

## 核心假设

- **H1** 在游客占比高的城市，店铺公开评分与「本地人认可度」呈弱相关。
- **H2** 由地理分层、结构特征、时段热度构造的复合信号，对本地人认可度的预测能力
  显著优于评分基线。
- **H3** 在低预算区间（人均 ≤ 30 元），评分与本地认可度的背离程度显著大于高预算区间
  （人均 ≥ 60 元）。

## 三层数据的定位（有意区分）

| 数据层 | 类目码 | 条数 | 在项目中的角色 |
|---|---|---|---|
| 餐饮店铺 | `050000` | 9,560 | **研究对象**：标注、建信号、做实验 |
| 景点 | `110000` | 643 | 约束数据：只用于行程排程，不标注、不进实验 |
| 住宿 | `100000` | 3,612 | 约束数据：只用于预算分层 |

交通、天气、节假日属于环境数据，不进仓库。

## 快速开始

```bash
# 1. 自备高德【Web 服务】类型 Key，写入仓库根目录 key.txt
#    （不要用 Web端(JS API) 类型的 Key，会 403）

# 2. 采集（按层分别跑，--report-only 只重建报告不消耗配额）
python scripts/amap_poi_collect.py --layer food
python scripts/amap_poi_collect.py --layer scenic
python scripts/amap_poi_collect.py --layer hotel

# 3. 清洗 + 分层抽样（随机种子固定，结果可复现）
python scripts/make_sample.py --n 150 --seed 20261021

# 4. 生成扫街路线表
python scripts/make_route.py
```

依赖：Python 3.10+、`pandas`、`openpyxl`、`python-docx`（仅生成文档时需要）。
采集脚本只用标准库，零额外依赖。

所有脚本的路径都基于脚本自身位置解析，**可以在任何工作目录下运行**。

## 前端（网站骨架）

`web/` 是一个 Vue 3 + Vite 单页应用，数据读 `web/public/data/` 下的静态 JSON，
**不需要后端、不需要高德 Key、不联网也能跑**。

前置：[Node.js 18+ LTS](https://nodejs.org/)。装好后执行一次 `corepack enable`，
即可获得与 `package.json` 中 `packageManager` 字段一致的 pnpm 版本（无需单独装 pnpm）。

```bash
python scripts/export_web_data.py     # 1. 生成/刷新前端数据
cd web
pnpm install                          # 2. 装依赖（首次）
pnpm run dev                          # 3. 打开 http://localhost:5173
```

构建：`pnpm run build` → `web/dist/`。已设 `base: './'` + hash 路由，
产物可直接放进 GitHub Pages 子路径，无需服务端配置。

**当前进度**：站点骨架、数据导出、片区列表与店铺详情已完成；
规则版行程生成（Step 3）尚未实现，`/itinerary` 页面会明确说明，不提供假行程。

两条设计约束：

1. **数据诚实标记**：没标注过的店显示「本地认可度 待采集」，
   **绝不用平台评分顶替** —— 否则这个站就变成了它自己要反对的东西。
2. **单一数据入口**：页面只通过 [`web/src/data/provider.js`](web/src/data/provider.js) 取数，
   将来接 Java 后端 API 时只改这个文件，页面一行不动。

字段契约见 [`web/src/data/schema.md`](web/src/data/schema.md)。

## 数据来源与合规声明

- 数据来自**高德开放平台 Web 服务 API**，使用个人开发者额度，遵守其服务条款。
- **不采集**：任何需要登录的数据、平台明令禁止抓取的内容、用户评论正文、个人身份信息。
- API Key 通过 `key.txt` 或环境变量 `AMAP_KEY` 提供，**不入库**（见 `.gitignore`）。
- 采集频率限制为 0.35 秒/请求，不构成对服务端的压力。
- 商铺信息仅用于学术研究与技术演示，不含商业用途。

## 已知数据限制

- 接口单次查询最多返回 200 条，密集商圈存在欠采样；已用网格平铺缓解，但非 100% 覆盖
  （food 层有 52 个网格仍触顶）。
- 评论正文与历史客流无法通过接口获取，改用人工实地采样替代。
- 住宿房价字段缺失率 **99.8%**，无法用于预算分层，拟改用酒店类别 / 星级作为价格代理。
- 景点类目存在噪声（部分零售店铺被标注为风景名胜），需人工过滤。
- 景点票价字段缺失率 97.7%，主要景点门票需手工补充。
