# 一页纸提案：面向网红城市的本地偏好餐饮 POI 可信度评估与行程生成——以长沙为例

> 用途：找导师沟通 / 毕设开题雏形 / 后续简历的项目描述来源
> 状态：v1 草稿，方括号【】处待你填写或与导师确认

---

## 一、一句话说明

在网红城市中，主流平台的餐饮评分被游客流量、商家运营与刷评严重污染；本项目构造"本地偏好信号"来评估餐饮 POI 的真实可信度，并据此生成节假日可执行的行程。

---

## 二、背景与要解决的问题

**现象**：长沙这类网红城市里，评分最高的店往往不是本地人吃的店。坡子街排队三小时的店 vs 冬瓜山、四方坪本地人天天光顾的粉店与小炒，存在系统性偏差。

**现有评分的四个缺陷**：

1. **刷评与商家运营**：评分可被购买和运营，越高分反而越可疑。
2. **游客权重过高**：游客是一次性消费，关心环境、打卡、出片，而非"会不会再来"。游客评价数量上碾压本地评价。
3. **幸存者偏差**：不好吃的店被淘汰后不再产生评价，评分分布上移。
4. **无时序区分**：节假日与工作日的客群完全不同，但评分是混在一起的。

**核心洞察**：本地人的**重复消费行为**不会骗人，但这个信号不在公开评分里，需要重新构造。

---

## 三、问题定义（可验证的假设）

- **H1**：在游客占比高的城市，店铺的公开评分与其"本地人认可度"相关性弱（预期 Spearman ρ < 0.4）。
- **H2**：结合地理分层、评论文本、时段热度差构造的复合信号，对"本地人认可度"的预测能力显著优于评分基线。

**验证方式**：人工标注 ground truth，比较 Precision@10 / NDCG@10，并做消融实验。

---

## 四、方法（5 步）

| 步骤 | 内容 | 产出 |
|---|---|---|
| 1. 数据采集与对齐 | 高德 POI / 路径规划 API、公开统计数据、节假日日历；多源数据实体对齐 | 统一 POI 表 |
| 2. 信号构造 | 见下方 TPI 设计 | 店铺特征表 |
| 3. 可信度评分 | 加权/学习排序，输出可信度分与排序 | 评分服务 |
| 4. 行程生成 | 带约束的多目标排程（时间窗、营业时间、距离、口味多样性、排队容忍） | 行程方案 |
| 5. LLM 事实校验 | 逐条校验营业状态、营业时间、距离合理性，抑制生成幻觉 | 校验报告 |

**TPI（游客污染指数）候选信号**：
- **地理**：到游客核心区（五一广场/坡子街）的距离与引力衰减
- **文本**：评论中"本地生活词"vs"游客打卡词"的词频比
- **时序**：节假日热度 / 工作日热度 的比值（越低越本地）
- **时长**：开业年限、菜单稳定性
- **结构**：连锁化程度、外卖占比、【待定：是否纳入价格带】

> 【待定】最终信号集建议先做相关性筛选，只保留 4–6 个，避免过拟合与解释困难。

---

## 五、数据方案

**来源（合规优先）**
- 高德开放平台：POI 检索、路径规划、地理编码（需申请 key，注意配额）
- 公开数据：统计年鉴、文旅部门公开信息、天气、节假日日历
- **明确不做**：爬取大众点评 / 小红书等需登录或明确禁止抓取的平台

**自建标注集（本项目的核心资产）**
- 规模：长沙 **150 家**餐饮店铺（下限 80 家）
- 片区划分：五一广场/坡子街｜南门口｜冬瓜山｜四方坪｜河西大学城｜开福区
- 标注维度：本地人认可度（1–5）、游客浓度（1–5）、是否网红店、是否连锁、口味标签、人均价、营业时间稳定性
- 核验方式：实地到店 + 电话核验 + 与本地受访者交叉验证

**采集时间窗（关键，一年只有一次）**

| 时段 | 客群状态 | 用途 |
|---|---|---|
| 2026.11–12 周末 | 淡季日常 | 基线 |
| 2027.1 中旬（寒假初） | 本地日常 | 基线复测 |
| 2027.2 上旬（春节） | 游客峰值 | **对比峰值，最有价值** |
| 2027.2 下旬（节后） | 回落 | 信号稳定性验证 |

## 六、评估指标

**离线（主要）**
- Precision@10、NDCG@10
- 基线：① 公开评分排序 ② 评论数排序 ③ 销量/热度排序
- 消融：逐个去掉信号，观察指标下降幅度

**在线（小样本）**
- 10–20 人用户测试：行程可行率、满意度（Likert 5 级）、是否愿意按行程执行

**工程**
- 接口 P95 延迟、数据更新时延、标注一致性（多人标注 Kappa）

---

## 七、系统设计（Java 后端为主）

- **后端**：Java 17 + Spring Boot 3 + MyBatis-Plus + PostgreSQL + PostGIS + Redis
- **数据处理**：Python 离线脚本计算信号表，落库；后端只做查询与组装（**刻意切分，降低 Java 侧难度**）
- **前端**：Vue3 + 高德 JS API（模板改造，不自研地图）
- **部署**：Docker Compose + 单台云服务器，提供公网可访问 Demo
- **模块**：POI 服务 / 信号计算 / 评分服务 / 行程生成 / 用户与收藏

| 风险 | 应对 |

| 高德 API 配额不足 | 缩到 3 个片区，降低调用频次 |
